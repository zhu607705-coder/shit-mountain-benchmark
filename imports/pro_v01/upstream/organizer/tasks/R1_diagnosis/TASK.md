# R1 · 八次检查，找出真正值得修的故障

## 参赛题面

一个服务集群出现异常。探针会误报和漏报，一次事故可能没有故障、只有一个故障，也可能同时有两个。你获得服务候选集、各故障组合的先验概率、探针对各组合的条件响应概率、检查费用和修复损失表。真实故障组合不公开。

你需要逐次选择检查，观察检查结果，再决定继续调查或修复哪些组件。最多 8 次检查，总检查费用不得超过 9 个成本单位；允许提前停止，允许重复同一探针。最多修复两个组件。目标是最小化检查成本、漏修损失与误修代价，而不是写最长的推理报告。

接口为 act(public_model, history, remaining_budget)，返回 {"test": 整数索引} 或 {"repair": [组件索引]}。模型可以直接与此接口进行 JSON 交互；示例策略以 Python 实现。

public_model.json 包含完整字段示例。history 的每一项为 {"test": j, "positive": true/false}。测试之间在给定隐藏组合时条件独立，同一测试的重复测量也使用新观测。给定模型文件中的概率和损失是题目的正式语义。

## 什么算难

单个高相关报警不保证是最值得检查的位置。共同探针可能同时覆盖几个组件；一次看似不划算的检查可能使下一次检查非常有价值。修复两个最高后验概率组件也不一定最便宜，因为漏修代价不同。策略需要决定何时停止收集信息。

## 判分

单次 loss = 所有检查费用 + terminal_losses[修复动作][隐藏故障]。先在固定隐藏实例上求平均和最差十分位均值，再按 RULES.md 合并。错误诊断不自动判零，它按后果扣损失。超预算、非法探针和非法修复集合违反硬约束。

## 我提供的基线

baseline.py 逐次做贝叶斯更新，然后计算所有修复动作的后验期望损失。对每个检查枚举阳性/阴性两种结果，选取“检查费 + 一步之后的最小修复损失”最低的动作；若没有检查值得做，立即修复。是 myopic value-of-information，不是全局最优策略。

本次原型在 3 个公开生成模型、共 90 个抽样事故上运行。结果见 ../../results/R1_baseline.json；不检查直接按先验修复的参照见 R1_no_queries.json。真值只由模拟器使用，策略接口不接收真值或种子。

## 高难档（计划规格，未在本次结果中执行）

16 个组件，含成对故障；检查预算维持紧张。改变探针覆盖结构、风险比和误报率，使用未见的服务命名与组合；对跨两步才有价值的探针安排专门场景。至少 10 个独立模型族，每族多个事故。评估策略搜索的计算成本，但不得泄露未来检查结果。

## 可以超过基线的方向

两步/多步前瞻，信念状态搜索，风险敏感的停止准则，以及针对低概率高损失故障的检查分配。任何方案仍须使用相同可用信息与预算。
