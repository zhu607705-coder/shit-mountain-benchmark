# F1 · 凌晨事故控制台：一万条告警之后，谁还能看清现场？

你接手了一套值班控制台。03:12，一次数据库配置变更触发了跨服务故障。告警、重复重试、恢复探针和无关噪声混在一起；值班同学在切换筛选后确认错了事件，刷新页面又丢了现场。交接班时，双方打开同一个链接，看到的不是同一个状态。

你可以修复 `starter.html`，也可以重新设计。**方向是帮助值班人员更快、更可靠地恢复现场理解。没有指定截图、唯一信息架构或唯一最优解。** 不评框架品味，评可验证的任务完成能力与盲评中的实际使用体验。

## 交付

- 一个可运行网页及完整源码、启动说明；可以提交单文件 HTML。
- 使用公开 `data.json` 的全部 **10,000 条**记录，不能抽样后假装是全量。
- 自动化脚本或清楚的操作回放，说明真实跑过什么。
- `result.json`：`valid`、`machine_score`、`human_visual_score`、`raw_score`、`checked`、`pending`、`known_failures`。未经独立盲评时，后两种评分保持 `null`。
- 清楚说明适用设备、数据持久化、错误处理与尚未解决的边界。

## 必须解决的现场问题

1. 一万条事件可浏览、筛选、搜索，严重程度、服务和确认状态联动；结果必须和固定数据一致。很长的内容和字面量 `<img ...>` 不得破坏页面或执行代码。
2. 列表复用、滚动、筛选不能让事件身份漂移。确认的是稳定事件 ID；键盘、鼠标和触屏都能完成核心任务。
3. 链接能够保存筛选和选中事件；刷新、前进、后退后能恢复。空结果和无效 URL 要有明确表现。
4. 事件与上下游关系必须可追溯。数据的 `parent` 仅表示本次合成注入的已知关系；不能从时间相邻自行宣布根因。
5. 确认状态持久保存，支持撤销确认；存储失败不能显示“已保存”。两个窗口确认不同事件时，两个操作都应保留。
6. 360 px 窄屏可以完成搜索、选择、查看证据和确认；用户不需要靠缩放或精确拖拽才能操作。

## 数据约定

`data.json` 是唯一公开事实源。所有数据均为合成：事件顺序是回放序号，不承诺按时间单调排序。前 6 条构成事故 `TR-INCIDENT-042`，其余事件提供大量噪声。`EVT-00001` 包含长文本；`EVT-00043` 包含必须作为普通文字显示的 HTML 外观字符串；`EVT-10000` 用于检验末端记录。初始确认集合为空。

未知 URL 参数可以忽略；无效枚举不能导致崩溃。对于筛选后不存在的选中项，可选首条或清空，但必须一致并明确，不能继续显示一个看似仍属当前筛选的旧事件。

## 旧系统的已知问题

`starter.html` 只显示最前 80 条记录，却标为“10000 条”；搜索把输入当成正则表达式；选中项按当前列表索引保存；确认状态依附当前行；刷新丢失；因果信息只显示模糊文本；全部数据载入和错误状态没有契约。你可以发现额外问题，不必保留旧布局。

## 比赛条件

建议独立限时 90 分钟、最多 40 次工具动作或 40,000 输出 token（主办方赛前统一选择一种预算）。浏览器基准 Chromium、1440×1000 与 390×844，并加测 360×800；第三方网络禁用。可用任何能本地构建的技术栈。模型不得读取其他参赛者提交或评委结果后定向调参。

公开题用于可复现对比，不应声称已构成抗污染的正式 benchmark。正式轮应私下更换数据 seed、服务名、关系分支、恶意字符串和窗口竞争时序，评分语义保持一致。主办方必须在提交前冻结测试与评分，不能看过答案后临时增加门槛。

评测见 `rubric.md`。参考实现不是标准答案。
