# C2 事故单：构建服务换一个环境就失效

这是为本挑战赛编写、人工植入状态缺陷的合成仓库，不是对真实公司的生产事故记录。参赛起点为 `repository/buggy/`；不要先读修复版。

运维交接时留下了以下症状。它们不保证一条症状只对应一个错误，也不提供唯一修复架构。

1. 在开发者目录里能完成一次构建，web 与 worker 分开部署后，HTTP 一直显示 `pending`，worker 却没有报错。
2. 反向代理配置了 `/build/v2`，进程启动正常，健康检查却返回 404。
3. 两个项目都用了 `main`，其中一个项目偶尔拿到另一个项目的向量结果；审计人员还发现换项目 URL 后能查到不属于该项目的作业。
4. 用户看到 `running` 后点取消，最终页面有时又变回 `done`。再次构建能否恢复也不稳定。
5. 队列积压时修改图，先入队的任务有时拿新图计算；点击构建时看到的图不等于实际执行图。
6. worker 进程中断后，某些任务永远卡在 `running`。重启 HTTP 进程似乎不起作用。
7. 一台已有数据的机器升级后无法启动，日志出现 `no such column: payload`。删除数据库可以启动，但这种操作不能接受。
8. 某个依赖先失败再被修复，服务可能返回成功空向量；曾经缓存过结果的图在改节点、改别名或改变取消条件后也会出现旧结果。

可观察边界：HTTP 项目/作业接口、web 与 worker 的独立启动目录、配置文件、SQLite 持久化文件、进程 stdout/stderr、原核心 API。允许增加日志、断言和自测；每个判断应有最小复现或状态证据。请保留旧项目与作业记录，不要用删库、清空所有状态或跳过取消等方式掩盖问题。
