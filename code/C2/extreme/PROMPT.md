# C2：排队的是旧图，取消的是旧任务，恢复后跑的却是新结果

**完整 extreme 资格必须同时通过 [stage-v2取消恢复与不可变图身份协议](STAGE_PROTOCOL.md)。** 提交目录的 `extreme.py` 有公开故障starter：单独取消重试、单独改图均通过，取消后改图再恢复会发布旧值。旧基线无此接口时标capability_gap；深DAG压力只占另一部分。

这是统一 C2 的扩大环境，保留原服务仓库、图语言、HTTP 接口、结果所有权与左到右错误语义。原题 500 节点、200 层路径扩到 **5,000 节点、2,000 层路径**，各 10 倍；项目扩大到 20 个、每项目 20 次图版本变化，同时有 4 个 worker。新多 worker 环境不再适用原题“只有一个 worker”的部署假设。

## 事故链

1. 从旧 schema 原地升级，为每个项目保存图，立即入队一个任务。入队后替换图中的别名，让同一个 `main` 指向另一个节点。下一轮修改图又重新入队。队列里同时存在多个看起来相似、语义不同的版本。
2. 在还未运行时取消一部分旧任务。多个 worker 启动后，再取消一个已经观察到 running 的任务，并强杀其中一个 worker，启动替代进程。恢复过程必须区分仍有存活所有者的任务、失去所有者的任务和已经被取消的任务；终态不能被晚到结果覆盖。
3. 旧队列消化后，对每个项目提交重试。重试必须使用最新图和别名，不能继承旧任务的取消状态，也不能命中另一个项目或旧图的结果。重启 HTTP 服务之后重新读取这些结果。
4. 最后通过同一个真实服务提交 5,000 节点共享 DAG。输出只有两个整数，复杂度来自依赖、调度、缓存和生命周期，避免拿大输出撑爆内存充数。深图的递归栈问题明确属于规模边界，并不单独构成“思考难度增加”的证据。

难点在于把**项目身份、不可变图版本、任务身份、取消作用域、worker 所有权与缓存内容**分开，然后证明它们在恢复路径上仍能正确组合。只在执行时重新读取“当前图”、启动时一律重置 running、取消时随便清空整个缓存，都会有不同的正确性或效率代价。

## 候选接口与允许实现

从 `code/C2/repository/buggy` 复制整个仓库。保留 `cli.py serve|worker --config FILE`、配置相对路径/base_path、HTTP API、`engine.py:Engine` 以及 `../CORE_CONTRACT.md` 中的全部指令。只扩大节点数、路径深度和多 worker 部署。允许自行设计持久领取权、续约、恢复、版本地址缓存和调度结构，不规定唯一算法或数据库表。

已取消任务永远不能回到 done；已排队任务使用入队快照；新任务使用最新图；跨项目读取 404；恢复后成功结果仍存在。计算可以内部重试，外部只可观察到符合业务合约的终态，不能把物理 exactly-once 执行作为不可验证口号。全部机器正确性仍需通过原题回归。

## 运行与提交

```bash
python3 code/extreme.py --task C2 --scale smoke --seed 260926 --output c2.json
python3 code/extreme.py --task C2 --scale full --seed 260926 --submission my_submission --output c2-full.json
python3 code/extreme.py --task C2 --scale full --export /tmp/c2-public
```

smoke 保留完整交错链，使用 3 项目×3 版本和 1,200 节点/1,100 深度；full 生成并提交实际 5,000 节点图及 400 个排队快照，不把设定值当已通过证据。导出包含可运行 starter、兼容合约、实际 scenario、无答案的观察型smoke和启动说明。

交付修复仓库、跨 API/数据库/worker/核心图的 `DIAGNOSIS.md`、独立自测和 `TEST_REPORT.md`。必须提供故障复现与修改前后同命令结果。旧递归基线若在深图返回 RecursionError，这只是一个公开待修缺陷；修掉栈深度还要过版本/取消/恢复完整链。

## 验收与分数边界

独立迭代 oracle 为所生成的 input/scale/sum DAG 计算期望；微型 8 节点例可以手算 `[12,20]`，证明生成任务可行。实际任务都经 HTTP 入队，由独立 worker 执行，不以纯函数 mock 替代环境验收。

v0.2 机器合约质量 **Q = 100，当且仅当扩大后的旧接口检查和必需 stage-v2 全部通过；否则 Q = 0**，写入 `raw_score` 和 `quality_score`。`machine_pass_rate` 只用于诊断，不能将缺失接口或错误结果用平均通过率抵消。

不同正确实现由独立 host 的 Codex 评分流程结合 Agent 耗时和 token 区分效率；本裁判运行耗时不是模型思考时间，不恢复未标定的吞吐、延迟或内存 bonus。正式比较使用冻结 full 轮次，smoke Q 只表示调试子集。当前公开场景不保证覆盖所有调度交错，未完成所有权审计的实现不能宣称生产级 exactly-once。执行器不是不可信代码安全沙箱。
