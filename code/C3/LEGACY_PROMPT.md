# C3 · Kill -9 之后，客户的数据还在吗？


## 参赛题面

继承一个本地键值存储。正常 CRUD 大多可用，但业务反馈：恢复后偶尔丢失已确认写入；重试会多提交一次；快照会被后来修改；压缩和删除组合后出现旧数据。请修复或重构 starter，不改变公开 API。

不用 SQLite、LMDB、RocksDB 或其他现成数据库。允许 Python 标准库；正式扩展赛可提供单独 Rust/C++组，不能混合运行时直接比原始速度。当前版本按 POSIX 单写进程定义，不要求网络分布式存储。


## API

Store(path) 打开写句柄；同一目录同时只能有一个写句柄。

commit(txid, ops) 返回递增版本号。ops 为 1–1024 项 put/del；put 的 key/value 为字符串。先验证整个批次，再写入。相同 txid、相同操作返回原版本；相同 txid、不同操作必须报错。此幂等记录跨重启和压缩保留。

get(key) 返回字符串或 None。snapshot() 返回保持创建时版本的对象，其 get 与 scan(prefix) 不受后续写入影响。scan 按 key 的 Unicode 码点顺序返回键值对。compact() 不改变任何可见内容、版本或幂等结果。close() 后写操作报错。


## 故障语义

commit 成功返回的数据必须在进程被 SIGKILL 后恢复。未确认事务允许完整出现或完全不出现，不能部分出现。进程中断造成的物理不完整尾部允许丢弃。完整记录出现校验损坏不能静默当成空库；可以明确报损坏。当前公开自检只覆盖进程故障，不宣称模拟真实断电和存储设备掉电语义。


## 当前验收

公开机制验收覆盖快照、原子验证、幂等冲突、删除压缩、同进程及真正跨进程写锁、相对路径打开后cwd变化、200次参考模型比对、4个SIGKILL时窗及确认后进程直接退出。与特定WAL格式相关的内部诊断不进入通用资格判定，也不要求参赛者采用同一格式。


## 高难档（未执行）

10 万以上键、8 个并行快照读者、256 MiB 运行内存、数千次故障注入；同时考查压缩峰值空间、恢复耗时和写放大。注入 I/O 错误与压缩发布窗口，验证之后继续写是否安全。磁盘耐久测试需要固定文件系统和实际存储配置，不能拿 tmpfs 的 fsync 耗时充当磁盘 TPS。


## 计分

丢失确认事务、部分事务可见、删除复活为关键失败。合格后比较扩展回归、吞吐、P99 延迟、峰值内存、恢复时间和空间放大。不得用一个平均“95%通过率”掩盖数据损坏。


## 本轮补全的接口与故障边界

模块导出Store、AlreadyOpen、CorruptionError。Store支持with上下文、version整数属性；Snapshot支持version、get(key)、scan(prefix='')。txid为非空字符串；op只能包含put的op/key/value或del的op/key，不允许未知字段。非法批次抛ValueError，已关闭句柄写入抛RuntimeError，已有写句柄时打开第二个抛AlreadyOpen。

Store(path)在打开时确定目录位置，相对路径不因调用者之后chdir而漂移。源数据目录为参赛进程可读写的POSIX本地目录；其他进程不能绕过Store API直接篡改活动存储。此范围并不要求抵御恶意宿主或目录替换攻击。

I/O异常后可以恢复继续，也可以将当前句柄置为必须关闭重开的失败状态；后者后续操作可抛RuntimeError。无论选择哪种，不能在部分记录之后或已经被替换的旧文件上继续确认新事务，导致确认数据在重开后丢失。格式无关验收不会指定WAL布局或强迫某种恢复算法。公开进程崩溃用例不等于真实掉电测试。
