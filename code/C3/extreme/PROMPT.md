# C3：压缩成功一半，重试之后历史交易复活了

**完整 extreme 资格必须同时通过 [stage-v2 writer代际与迟到压缩协议](STAGE_PROTOCOL.md)。** 提交目录的 `extreme.py` 有真实文件故障starter；压缩和writer迁移单独正确，迁移后的新ACK会被旧压缩迟到发布抹掉。旧Store基线通过下文I/O矩阵也不等于完成新资格。

沿用统一 C3 的 `Store(path)`、`commit(txid, ops)`、`snapshot()`、`compact()`、`close()` API，保留单写进程和同目录写锁，不得改用现成数据库。原题故障主要为 4 个强杀时间窗口；本环境构造 **12 条持久历史 × 6 个具体 I/O 切点 × 4 类故障 = 288 个故障历史**。这是已公布故障实例数量的 72 倍，含不同故障类别，不应误读为同分布难度的 72 倍。

## 事故经过与需要推理的关系

持久前缀包含写入、删除、事务 ID 重放，以及交错压缩。某个新事务同时写两个键并删除旧键，随后压缩可能生成并发布新的物理文件。故障后应用层仍尝试写入下一笔交易。如果错误被吞掉，内存看起来正确的下一笔 ACK 可能被写到已经 unlink 的旧 inode，重启后永久消失。

必须把四种状态区分清楚：调用者已收到 ACK、底层调用已完成但 ACK 未发出、物理部分写入、压缩已替换文件名但目录同步或句柄切换尚未完成。不能只根据异常类型决定“前一笔肯定没有成功”，也不能用重试生成新版本掩盖事务 ID 丢失。

## 可执行的阶段挑战

1. 在真实文件目录建立 100,000 个键。8 个快照读线程在写入/删除/压缩期间反复读取旧快照；另一个 OS 进程尝试获得写句柄，必须被拒绝。执行共 1,440 笔交易，压缩并重新打开后再逐笔重放，返回原版本。
2. 对 `commit` 的 write/fsync、`compact` 的 write/fsync、原子 replace 和目录 fsync 六处分别注入：调用前 EIO、调用完成后 EIO、ENOSPC（写入点先进行实际短写）、调用完成后 SIGKILL。
3. 每个切点前有不同的 tombstone/压缩/幂等前缀。错误后若实现还能返回新的 ACK，就必须证明它能跨重新打开保存；选择 fail-closed、要求关闭重开也是合法方案。
4. 独立新进程重新打开数据，检查稳定 ACK 前缀、未知结果交易“全部出现或完全不出现”、后续 ACK、删除不复活。然后重试原 txid、压缩、再重开，验证原版本和冲突检测。

本地测试明确是进程故障和真实系统调用边界上的异常注入，**没有模拟真实硬盘掉电**。8 个快照读者使用旧 API 对象，属于线程；另有独立进程写锁检查，不能把它说成 8 个多进程读句柄。

## I/O 适配与接口

提交 `engine.py` 或 `baseline.py` 导出 Store；目录提交会优先选择 engine.py。故障器拦截 Python `os.write`、`os.fsync`、`os.replace`，用 fd 类型区分文件和目录。它不要求 WAL 字节格式，也不读取候选内部字段。写路径若使用无法拦截的 native/mmap/缓冲实现，本项会标为 `capability_gap`，不能把未注入故障算作通过或算作认知难度证据；应提供等价可审计的 I/O 适配后再正式参赛。

```bash
python3 code/extreme.py --task C3 --scale smoke --seed 260926 --output c3.json
python3 code/extreme.py --task C3 --scale full --seed 260926 --submission my_store --output c3-full.json
python3 code/extreme.py --task C3 --scale full --export /tmp/c3-public
```

smoke 执行 24 个切点组合、32 键、8 交易和 2 快照读者。full 的 288 个 fault scenario、10 万初始键和 1,440 交易都真实生成；是否完整执行另行记录。不是把 12 条历史重复成空库故障：历史长度、删除目标、压缩位置和事务 ID 重放顺序会改变持久前缀。

## 交付和验收

除了完整可运行修复，提交逐阶段故障诊断、自测、旧回归和修改前后结果。解释线性化点、哪些结果未知、什么时候必须禁止继续确认、快照与压缩为什么不影响事务 ID。给出至少一条“局部修复看似正确，跨阶段组合仍损坏”的反例。

每条未知结果交易的独立 oracle 只有两个允许状态，微型实例可以人工检查，不预设文件布局。v0.2 机器合约质量 **Q = 100，当且仅当全部必需旧接口扩大检查与 stage-v2 都通过；否则 Q = 0**，写入 `raw_score` 和 `quality_score`。丢 ACK、部分交易、删除复活、幂等重放变版本及缺失代际接口均不能靠平均通过率补偿；`machine_pass_rate` 只作诊断。

不同正确实现的效率由独立 host 的 Codex 评分流程用 Agent 耗时和 token 记录计算。故障器执行时间、fsync 耗时和裁判重开时间不等于模型思考时间，不恢复未标定的吞吐、P99或空间奖励。正式成绩采用冻结 full 轮次，smoke Q 只是调试子集。基线通过的实际检查仍会保留。本执行器运行真实本地代码，不是安全沙箱。
