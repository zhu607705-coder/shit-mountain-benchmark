# 核心业务附录：仓库主任务以PROMPT.md的70/20/10评分为准

# C1：账已经对不上了——多租户事件账本修复

你接手一个经历三次供应商迁移的记账服务。入口承诺至少一次投递，历史事件会乱序重放，同一个租户的事件 ID 可能因迁移冲突出现多个版本；撤销也可能先于原始记录到达。遗留实现能跑正常演示，却会在真实组合场景下多扣钱、丢租户或污染余额。

**任务：修复 `buggy/`，提交一个保留接口、在公开合约内正确且尽可能快、内存占用低的实现。** 可以局部修补、重构或重写模块。没有指定数据结构、处理顺序或最优实现。接口输出有确定语义；算法和工程方案开放。

## 交付与接口

提交目录中必须包含 `engine.py`，导出 `solve(events: list[dict]) -> dict`。可添加标准库 Python 模块。提交入口：

```sh
python3 judge.py --submission baseline
python3 judge.py --submission /absolute/path/to/your_submission --output your_result.json
```

`events` 是一次完整账本快照；每次调用独立。输入是已经解析的 JSON，不含 NaN/Infinity、循环引用或非 JSON 对象。所有事件保证有非空字符串 `tenant`、`id` 和字符串 `kind`；其余载荷可能非法。规模上限：20,000 条事件、每条最多 32 项分录、标识及账户名不超过 128 个字符。无需实现网络接口、持久数据库或跨调用增量状态。

## 冻结的业务合约

1. 身份键是 `(tenant, id)`。将完整事件按 Python `json.dumps(event, sort_keys=True, separators=(",", ":"), ensure_ascii=False)` 规范化后的字符串作为载荷标识。对象字段顺序不重要，分录列表顺序重要，`1`、`1.0`、`true` 是不同载荷。完全相同的重复投递只处理一次。
2. 同一身份出现多个不同载荷时，整个身份为 `CONFLICT`，任何版本都不得产生余额影响。即使某一版本非法也先判冲突。冲突隔离不影响其他身份或租户。
3. `post` 必须且只能有 `tenant,id,kind,entries` 四个字段。`entries` 必须是至少两个 `[account, amount]` 组成的列表；`account` 是非空字符串；`amount` 必须是 Python `int` 且不能是 `bool`，绝对值不超过 10¹²。所有分录金额之和必须为零。同一账户可以出现多次。任一条件失败，整个身份为 `INVALID`，不得部分入账。聚合金额可能超过 2⁵³，必须保持整数精度。
4. `reverse` 必须且只能有 `tenant,id,kind,target` 四个字段，`target` 是非空字符串。它只寻找同租户、非冲突、合法的 `post`。找到则自身状态为 `APPLIED`，目标为 `REVERSED`，目标所有分录从最终投影中排除。多个合法撤销指向同一个 `post` 时，都为 `APPLIED`，只排除一次原账。撤销本身不生成分录。
5. 找不到上述目标的合法撤销为 `ORPHAN`。撤销撤销、跨租户查找、自引用、目标为非法或冲突身份，均不会改变任何余额。未知 `kind` 为 `INVALID`。不接受撤销的撤销来恢复原账。
6. 其余合法 `post` 为 `ACTIVE`。最终结果只取决于完整事件多重集合，与到达顺序无关。

返回对象只能包含：

```json
{
  "balances": [["tenant", "account", 123]],
  "statuses": [["tenant", "event_id", "ACTIVE"]]
}
```

`balances` 是所有 `ACTIVE` 分录的逐租户逐账户整数和，省略余额为零的行，按 `(tenant,account)` 的 Python 字符串顺序排序。`statuses` 包含每个出现过的身份且恰好一行，按 `(tenant,id)` 排序。输出 JSON 数字必须是整数，不能用浮点数或布尔值蒙混。

## 难点与验收

公开集包含冲突与撤销相互作用、跨租户同 ID、原子校验、重复分录、超浮点精确范围聚合、乱序与重复投递变形、36 组固定 seed 的组合场景，以及 8,552 条事件的混合负载。`fixtures/public.json` 与 `cases.py` 全部公开，seed `2026092601` **不是隐藏集**。

三项致命门槛的测试名称冻结为 `ordinary_post`、`tenant_namespace`、`invalid_is_atomic`。任一失败，`valid=false`，不参与正式相对排名；仍显示诊断原分。其他测试失败按正确率扣分，允许部分有效结果。公开裁判不以代码长度或是否复制基线结构评分。

设 `p` 为通过用例比例，`t` 为大负载 3 次 `solve()` 墙钟时间中位数，`m` 为一次独立 `tracemalloc` 测得的 Python 分配峰值：

- 原分基本项：`80 × p`。
- 只有全部正确时才解锁性能项：`10 × 0.03/(0.03+t) + 10 × 8388608/(8388608+m)`。
- 固定资源门槛：`t ≤ 2 秒`、`m ≤ 128 MiB`；超出时 `valid=false`、不发性能分。计时不含输入拷贝、oracle 与结果比较；内存从调用前开始跟踪，不含输入构造，也不等价于操作系统 RSS。
- 同一轮同一硬件、Python 版本、串行空闲测量；参赛有效结果按赛事总规则归一化，当前最好为 100。原分不是数学最优证明。

交付还应包含简短 `DESIGN.md`：解释一致性不变量、冲突策略、时间/空间复杂度和仍可优化的部分。该文档用于审查，不进入 v0.1 数值分，避免隐藏主观扣分。
