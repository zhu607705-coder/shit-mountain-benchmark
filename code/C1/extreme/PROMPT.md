# C1：迟到的旧 worker，把已经对好的账又写回去了

**完整 extreme 资格还必须通过 [stage-v2跨分片代际转账协议](STAGE_PROTOCOL.md)。** 提交目录新增 `extreme.py`；导出自带可运行故障starter。该starter单独处理ACK丢失和单独迁移都正确，二者组合会双扣，提供与规模无关的实测推理机制。下文是必须继续保持的原仓库扩大环境，单独通过不等于通过整个extreme。

这是统一 C1 的扩大环境，不是另起题号。原 HTTP、持久数据库、事件业务语义和诊断函数继续有效；参赛起点仍为 `code/C1/repository/buggy`。允许重构 API、队列、迁移、worker、投影和测试，但它们必须来自同一提交仓库。

## 事故链与阶段任务

第一轮先让三个初始化进程同时打开同一个 v1 数据库。服务升级后有一个 HTTP 请求已经提交，客户端却主动丢掉响应。它随后重放同一个请求，又有一个持不同载荷的冲突重试。你必须从持久状态判断究竟接收过什么，不能根据网络断开推断事务回滚。

第二轮让旧 worker 领取任务后被 SIGSTOP，租约过期后由新 worker 接手。新事件包含先到的撤销、后到的目标，以及使旧身份变为冲突的另一个载荷。新投影已经发布后，旧 worker 恢复。局部的“这个任务原来归我”和“我计算出的余额正确”都不足以授权它覆盖新状态。需要解释领取权、事件集合、提交事务和投影代际之间的不变量。

第三轮扩大到 20 个租户、20 个 worker、80 路 HTTP 提交线程、80 个到达轮次；每个租户每轮 80 个事件，共 1,600 个逻辑请求、128,000 个输入事件。每轮同时发出相同请求的多个副本，之后再重放确认 receipt。各租户重复使用相同 request_id 与 event_id。事件中的未来撤销、迟到冲突和非法金额共同改变历史分类，最后停止全部进程并重新启动。

v0.1 对应并发环境为 2 租户、2 worker、8 路 HTTP，因此这三个明确的配置轴各扩大 10 倍。配置、已生成的输入与实际执行数量会分别报告；并不声称任务的认知难度可以严格用倍数证明。

## 接口与行为目标

继续遵守 `../PROMPT.md` 和 `../CORE_CONTRACT.md`：`manage.py init|serve|worker`、全部 `/v1` 路由、配置环境变量、每批最多 200 个事件均保留。相对数据库路径以仓库为基准。进程暂停和恢复发生在本机 POSIX 环境。故障延迟仍使用 `LEDGER_WORKER_DELAY`；租约过期后新领取者能前进，旧领取者不能倒退 generation 或替换完成结果。

只有接收事务是幂等单位，网络请求可能重复；同键不同载荷应 409。跨租户查询必须 404。全部逻辑请求完成之后，持久投影必须等于**全部已接收不同事件载荷**的独立关系式解释结果；迟到冲突会使原记账与相应撤销重新分类，不能只看余额凑巧相等。旧库任务 ID/载荷必须保留。

## 本地入口

```bash
python3 code/extreme.py --task C1 --scale smoke --seed 260926 --submission code/C1/repository/baseline --output c1.json
python3 code/extreme.py --task C1 --scale full --seed 260926 --submission my_submission --output c1-full.json
python3 code/extreme.py --task C1 --scale full --export /tmp/c1-public
```

smoke 也会执行丢响应、租约抢占、旧 worker 恢复、冲突、撤销与重启，规模降为 3 租户/3 轮；不会假称已执行 full。export 生成可运行 starter、启动说明、无答案的观察型smoke和实际 `scenario.json`。

## 交付、验收与评分

交付完整仓库、补丁、`DIAGNOSIS.md`、自己的可运行回归测试和 `TEST_REPORT.md`。报告至少包含一条跨层因果链，说明为什么只修复其中一个局部故障仍不够；还需提供修改前复现、修改后同命令结果和原题全部回归证据。不要修改裁判。

机器检查记录迁移竞争、丢响应重放/租约交错、并发完整生命周期及必需 stage-v2 门槛。v0.2 机器合约质量 **Q = 100，当且仅当全部必需检查通过；否则 Q = 0**，同时写入 `raw_score` 和 `quality_score`。接口缺失、数据丢失、错租户、幂等冲突失守或代际倒退不能用其他成功比例抵消；`machine_pass_rate` 仅供定位。

正确实现之间的效率差异交由独立 host 的 Codex 评分流程，使用 host 记录的 Agent 耗时和 token；裁判自身启动、轮询和回归运行时间只是诊断值，不能冒充模型思考时间，也不恢复旧版未标定的性能奖励。正式比较采用冻结的 full 轮次，smoke 的 Q 仅表示该调试子集是否通过。

有独立账本关系式 oracle 和微型可行例。旧基线若通过这些机制，会如实报告通过；本题没有预设“必须击败基线”的判断分支，更没有无法解决的数学保证。所有运行均为真实 localhost HTTP、SQLite 和独立子进程。执行器只适合可信本地提交，不是安全沙箱。
