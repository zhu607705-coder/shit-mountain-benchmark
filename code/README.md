# 代码赛道：完整仓库中的定位、修复、自测与整体回归

主任务是接手一个能真实启动的 HTTP/SQLite/后台 worker 服务。模型需要从事故症状和公开测试复现问题，定位跨模块状态错误，提交补丁与自测，然后在不同环境下保持业务全流程可用。

| 题号 | 仓库 | 复杂环境与故障 | 仍保留的核心回归 |
|---|---|---|---|
| C1 | 多租户异步账本服务 | 请求身份、SQLite 迁移、工作目录、Unicode 路径、并发隔离、worker 中断恢复、重启持久化 | 乱序、重复、冲突隔离、撤销、原子校验与整数投影 |
| C2 | 持久化依赖构建平台 | API 前缀、配置路径、项目隔离、作业快照、运行中取消、失败重试、进程重启、旧 schema | 动态图、别名、缓存失效、错误次序、共享 DAG、返回值所有权 |

每题的 `repository/buggy/` 是主任务起点，`repository/baseline/` 是作者修复；外层 `buggy/` 和 `baseline/` 是最初核心模块参考。参赛者不需要照搬参考结构。数据与事故均为原创合成环境，不宣称来自真实企业仓库。

在每题目录运行：

```sh
python3 e2e_env_judge.py --submission repository/baseline
python3 judge.py --submission repository/baseline
```

前者创建临时工作目录与数据库、启动真实 API 和独立 worker，用 HTTP 执行业务流程及环境验收，结束后清理子进程；后者检查同一份仓库引擎的完整核心回归。换成 `repository/buggy` 可复现遗留缺陷。实际业务启动入口、API、环境变量和故障报告见各题 `README.md`、`PROMPT.md`、`INCIDENT.md`。

参赛必须提交 `DIAGNOSIS.md`、完整补丁、可执行自测、`TEST_REPORT.md`。定位报告把症状、复现输入、状态变化、代码位置和修复关联起来；测试报告保留修复前失败与修复后通过的命令和结果。公开测试允许阅读与运行，主办方封存测试与参考答案应当另行隔离。

仓库主分为环境业务链 70 + 核心回归 20 + 自测有效性 10。自测质量未完成自动或人工核验时保留 null，只报告已验证小计。最初核心裁判的速度/内存原分是诊断指标，不作为此版本仓库主分。完整计分见 [仓库赛道协议](../organizer/REPO_TRACK_PROTOCOL.md)。

所有 seed 和样例当前公开。真实本机进程测试不等于不可信代码安全隔离；正式线上赛仍需另行提供受限执行环境与冻结隐藏实例。当前包可用于本地试办和审查，不宣称生产托管、多机网络或跨操作系统已经验证。
