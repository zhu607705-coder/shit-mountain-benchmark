# 代码赛道：完整仓库中的定位、修复与自测

C1/C2 的主任务是接手有状态的完整服务仓库。最初的小型核心模块保留为回归检查，不能代表全部代码能力。

## 发给模型的材料

每题完整 `repository/buggy/`、该题题面、故障报告、公开配置与测试。允许阅读公开测试、日志、源码、数据库 schema，允许编写脚本复现；评测器的封存样例、参考补丁与主办方答案不进入参赛工作区。

病例可以提供多个症状，不预先告诉模型每个 bug 对应哪个文件。题目不是列一个 TODO 让模型逐行照做，而是要求它把运行证据连接到有问题的状态转换或模块边界。所有代码与业务数据均为本套题人工构造的合成环境，不宣称来自真实企业事故。

## 必须实际完成的工作流

1. **启动与复现。** 按仓库文档启动服务与 worker，观察 HTTP 响应、进程日志和持久状态，保留至少一条修复前失败的可复现命令。
2. **定位。** 在 `DIAGNOSIS.md` 中把症状、触发条件、错误状态/模块与代码位置连起来。允许不同根因组织方式，不强迫匹配主办方的措辞。
3. **修改。** 提交完整可运行仓库或补丁，保留公开 API 与功能，必要时正确处理旧数据库和配置兼容。
4. **自测。** 提交真实可运行的自测，以及 `TEST_REPORT.md`：修复前失败、修复后通过、相关回归、执行命令和仍有边界。只有文字“测试通过”不算证据。
5. **全流程验收。** 主办方在干净临时目录启动真实服务进程与 worker，用 HTTP 走完业务链，在迁移、重启、隔离或故障恢复环境下复放；最后执行同一份提交引擎的核心回归。

诊断文字用于定位证据审查，不因表达华丽加分；代码补丁和行为证据决定主要分数。不鼓励通过删掉异步、取消、隔离、持久化或缓存功能来让某条测试变绿。

## 分数及证据

- **环境与业务链 70 分：** 按每题公开矩阵检查真实 HTTP、数据持久化、后台执行、配置/路径、迁移、重启/恢复与隔离。致命门槛见各题；一般失败按环境通过比例扣分。
- **核心回归 20 分：** 调用实际仓库使用的同一份 `engine.py`，按既有正确率计分。不能给业务层换一个引擎，却用另外的旧基线测回归。
- **自测有效性 10 分：** 以可执行的回归测试、独立验证方式及对故障变体的检出能力为依据。每题写明自动变异检测或人工锚点。未实际完成质量判定则保持 null，已验证机器小计最多 90 分。

旧函数裁判的连续速度/内存原分仍保留，但在此版本只作辅助诊断，不与仓库主分混用。若未来加入性能主榜，需要单独冻结负载与机器后再发布新版本。

## 环境难度为何有价值

模型需要处理的失败包括：入口健康但 worker 从另一个路径读取了空数据库；空库可启动但旧 schema 升级失败；正常重试通过但进程被终止后任务无法恢复；单项目通过但别名或作业身份发生跨项目污染；取消请求返回成功但后来仍发布了结果。每题实际实现及注入情况以题面、源码和环境验收 JSON 为准，这些例子不是对尚未运行场景的通过声明。

当前仓库全部使用 Python 标准库，真实启动本机 HTTP 和 SQLite 工作流；这使第一版可以无额外服务安装直接试办。没有把线程/子进程称为容器隔离，没有声称已经覆盖真实多机网络、所有操作系统、生产数据库或 Kubernetes。增加这些环境应当保留现有业务契约，并单独提供可重放设施。
